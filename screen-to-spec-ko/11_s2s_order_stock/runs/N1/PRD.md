# PRD — 가나다식품 「주문 · 재고 백오피스」

> 「이 화면, PRD 로는 이렇게」 11편. 회사 · 직원 · 손님 · 상품 · 수량은 모두 교육용 가상 데이터.
> 형식은 10칸(개요 · 사용자 · 기능 · 화면 · 데이터 · 업무 규칙 · 제약 · 범위 밖 · 개발 단계 · 완료 기준).

## 1. 개요

- **배경:** 쇼핑몰 주문을 직원이 엑셀로 확정 · 출고하면서, 같은 상품의 마지막 재고를 두 사람이 동시에 확정해 재고가 -1 이 되고, 취소한 주문의 재고가 돌아오지 않는 일이 반복됐다.
- **목적:** 직원이 한 화면에서 주문을 **확정 · 출고 · 취소**하고 관리자가 **환불**하면, 재고는 **정해진 시점에만** 바뀌고 **0 미만이 되지 않는다**.
- **성공 기준:** 마이너스 재고 0건. 취소 뒤 재고 불일치 0건.

## 2. 사용자

- **직원 · 관리자 2유형.** 로그인 없이 화면 위 **사용자 선택 상자**에서 고른다. API 는 요청자를 본문의 `user`(user_id)로 받는다. **로그인은 8 범위 밖.**
- 직원은 확정 · 출고 · 취소, 관리자는 그에 더해 **환불**.

## 3. 기능 요구사항

| 번호 | 기능 | MoSCoW | Phase |
|---|---|---|---|
| F1 | 주문 표: 주문 번호 · 손님 · 주문 시각 · 줄(상품 · 수량) · 상태 · 그 상태에서 할 수 있는 동작 버튼 | Must | 1 |
| F2 | 재고 패널: 상품마다 현재 재고 | Must | 1 |
| F3 | 동작: 확정 · 출고 · 취소 · 환불 — 결과(바뀐 주문과 재고)를 바로 다시 그린다 | Must | 1 |
| F4 | API: `GET /api/users` · `GET /api/products` · `GET /api/orders` · `POST /api/orders/{order_id}/{action}` (`action` = `confirm` · `ship` · `cancel` · `refund`) | Must | 1 |

## 4. 화면

한 페이지(`/`). 위 사용자 선택, 왼쪽 주문 표, 오른쪽 재고 패널.

- **사용자 선택:** `data-testid="user"` (`<select>`, option 의 value 는 user_id). 처음엔 첫 번째 사용자.
- **주문 줄:** `data-testid="order"` + `data-id`(order_id) + `data-status`(placed · confirmed · shipped · cancelled · refunded). 안에 상태를 한글로(접수 · 확정 · 출고 · 취소 · 환불), 동작 버튼 `data-testid="act-confirm"` · `act-ship` · `act-cancel` · `act-refund` — **그 상태에서 할 수 있는 것만** 보인다(안내일 뿐, 막는 건 서버).
- **재고:** 상품마다 `data-testid="stock"` + `data-id`(product_id), 안에 재고 숫자.
- **메시지 줄:** `data-testid="message"` — 서버가 거부하면 `detail` 그대로.
- **오류 상태:** API 가 실패하면 `불러오지 못했습니다` 와 다시 시도 버튼.
- 문구를 테스트하는 요소는 그 문구가 **손잡이 요소 안에** 있어야 한다.

## 5. 데이터

- **원본:** 프로젝트 루트 `seed/` CSV 4개. 서버는 **시작할 때마다** CSV 를 읽어 SQLite(`backoffice.db`)를 **새로** 만든다. 동작 결과는 DB 에 쓴다(서버가 도는 동안 유지).
- `stock` 은 **지금 출고할 수 있는 수량**이다. CSV 의 확정 · 출고 주문은 이미 차감된 뒤의 값이다.

| 파일 | 칸 | 형식과 예시 |
|---|---|---|
| `seed/users.csv` | `user_id, name, role` | `user_id` 문자열 `u1` · `role` `staff` 또는 `manager` |
| `seed/products.csv` | `product_id, name, stock` | `product_id` 문자열 `P01` · `stock` 0 이상 정수 `10` |
| `seed/orders.csv` | `order_id, customer, status, ordered_at` | `order_id` 문자열 `O-1001` · `status` `placed` · `confirmed` · `shipped` · `cancelled` · `refunded` 중 하나 · `ordered_at` `2026-10-24 09:10` |
| `seed/order_lines.csv` | `order_id, product_id, qty` | `qty` 1 이상 정수 · 한 주문에 줄 여러 개 |

- **테이블:** 접두어 `bo_` — `bo_users` · `bo_products` · `bo_orders` · `bo_order_lines`.
- **가상 데이터:** 사용자 3명(직원 2 · 관리자 1), 상품 5개(재고 0 인 상품 1), 주문 8개 이상(상태 다섯 가지가 다 있게). **같은 CSV 를 다른 내용으로 바꿔 끼울 수 있어야** 한다.
- **API**
  - `GET /api/users` → `[{"user_id","name","role"}]`
  - `GET /api/products` → `[{"product_id","name","stock"}]`
  - `GET /api/orders` → `[{"order_id","customer","status","ordered_at","lines":[{"product_id","name","qty"}]}]` 주문 시각 오래된 순
  - `POST /api/orders/{order_id}/{action}` 본문 `{"user":"u1"}` → 200 `{"order": {주문 하나, 위와 같은 모양}, "products": [재고 전체]}`
  - 거부 응답은 모두 `{"detail": "사유"}`.

## 6. 업무 규칙

| 번호 | 규칙 |
|---|---|
| R1 | **상태와 동작.** 확정 `confirm`: 접수 → 확정 · 출고 `ship`: 확정 → 출고 · 취소 `cancel`: 접수 또는 확정 → 취소 · 환불 `refund`: 출고 → 환불. 그 밖은 409 `지금 상태에서는 할 수 없습니다`. |
| R2 | **재고는 확정할 때 줄인다.** 줄마다 수량만큼. **한 줄이라도 모자라면** 409 `재고가 부족합니다: <상품 이름>` 이고 **아무것도 바뀌지 않는다**(앞 줄도 줄이지 않는다). 접수만으로는 재고가 바뀌지 않는다. |
| R3 | **취소하면 되돌린다.** 확정이었던 주문을 취소하면 줄마다 수량만큼 재고를 되돌린다. 접수였던 주문은 재고 그대로. |
| R4 | **환불은 재고를 되돌리지 않는다.** 돌아온 상품의 검수 · 재입고는 8 범위 밖. |
| R5 | **재고는 0 미만이 되지 않는다** — 여러 확정이 **동시에** 와도. 재고 3 인 상품에 확정 8건이 한꺼번에 오면 3건만 성공한다. |
| R6 | **권한.** 확정 · 출고 · 취소는 직원 · 관리자. 환불은 관리자만 — 직원이면 403 `관리자만 할 수 있습니다`. |
| R7 | **입력.** 본문에 `user` 가 문자열로 없으면 400 `사용자를 확인하세요`. |
| R8 | **거부가 둘 이상 해당하면 '무엇을 찾아야 알 수 있나' 순서로 하나만:** 본문만 보면 아는 것(400) → 없는 주문 · 없는 사용자 · 없는 동작(404) → 사용자를 찾아야 아는 권한(403) → 주문 상태 · 재고를 봐야 아는 것(409). |

## 7. 제약

- 스택: **Python FastAPI + 순수 HTML/JS(프레임워크 · 빌드 도구 없음) + SQLite.** 수량은 정수.
- 실행: 프로젝트 루트에서 `python -m uvicorn main:app --port 8000` (`main.py` 에 `app = FastAPI()`). 포트는 환경 변수 `PORT` 가 있으면 그것.
- 외부 네트워크 · CDN 없음. 외부 패키지는 `fastapi` · `uvicorn` 만. 한글 UI.

## 8. 범위 밖 (Won't)

- 로그인 · 회원, 주문 만들기 · 고치기(주문은 CSV 로만 들어온다), 결제 · 환불 금액 계산, 반품 검수 · 재입고, 부분 출고 · 부분 취소, **상품 · 재고 편집 화면(데이터 편집 화면)**, 재고 알림, 배송 추적, 엑셀 내려받기, 다크 모드.

## 9. 개발 단계

1. **Phase 1:** `seed/` → SQLite, API 4개와 규칙 R1~R8, `/` 화면(사용자 선택 · 주문 표 · 재고 · 메시지 · 오류).
2. 그 외 없음.

## 10. 완료 기준 (DoD)

`tests/test_dod.py` 가 완료 기준이다. 아래 9개가 모두 통과해야 끝난다.

- [ ] T1 `/` 가 200 으로 열리고 '주문' 이 보인다.
- [ ] T2 사용자 3명(역할 포함) · 상품 5개 · 주문 전체와 줄이 계약대로 나온다.
- [ ] T3 확정하면 줄마다 재고가 준다. 한 줄이라도 모자라면 409 이고 다른 줄의 재고도 그대로, 주문은 접수 그대로 (R2).
- [ ] T4 확정 주문을 취소하면 재고가 돌아오고, 접수 주문을 취소하면 재고 그대로, 출고 주문의 취소는 409 (R1 · R3).
- [ ] T5 직원의 환불은 403, 관리자의 환불은 200 이고 재고 그대로, 취소 주문의 환불은 409 (R4 · R6).
- [ ] T6 접수 주문의 출고는 409, 같은 주문을 두 번 확정하면 두 번째는 409 이고 재고는 한 번만 준다 (R1 · R2).
- [ ] T7 재고 3 인 상품에 확정 8건을 동시에 보내면 정확히 3건만 200, 재고 0 (R5).
- [ ] T8 본문 없음 + 없는 주문은 400, 없는 주문은 404, 없는 사용자는 404, 직원이 접수 주문을 환불하면 403(409 아님) (R7 · R8).
- [ ] T9 화면: 접수 주문의 확정 버튼을 누르면 그 줄의 상태가 확정이 되고 재고 숫자가 줄며, 재고가 모자란 주문을 확정하면 메시지 줄에 `재고가 부족합니다` 가 보인다.
