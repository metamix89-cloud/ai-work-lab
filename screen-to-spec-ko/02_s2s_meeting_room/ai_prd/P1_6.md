# 회의실 예약 웹앱 PRD

- 회사: 다온소프트 (사내용)
- 문서 상태: 초안 v0.1
- 작성일: 2026-10-30

## 1. 개요

### 1.1 배경과 목적
회의실 3개를 쓰는데 예약 방법이 따로 없어서 겹치거나 비어 있는지 알기 어렵다. 한 화면에서 오늘 시간표를 보고, 빈 칸을 눌러 바로 예약하고, 내 예약은 직접 취소할 수 있는 작은 웹앱을 만든다.

### 1.2 요청 요약
- 회의실 3개의 하루 시간표(9시~18시, 30분 단위)를 보여 준다.
- 빈 칸을 누르면 예약된다.
- 내 예약은 취소할 수 있다.

### 1.3 기술 스택
| 영역 | 선택 |
|---|---|
| 백엔드 | Python FastAPI |
| 프론트엔드 | 순수 HTML/JS (프레임워크·빌드 도구 없음) |
| 데이터베이스 | SQLite (파일 1개) |
| 데이터 | 가상 데이터만 사용 (실제 직원·회의실 정보 사용 금지) |

### 1.4 성공 기준 (한 줄)
처음 쓰는 직원이 설명 없이 1분 안에 빈 칸을 눌러 예약하고 취소까지 해 볼 수 있다.

## 2. 사용자

| 구분 | 설명 | 할 수 있는 일 |
|---|---|---|
| 직원 | 다온소프트 임직원 (가상 사용자 5명으로 시작) | 시간표 보기, 예약, 내 예약 취소 |

- 관리자 역할은 두지 않는다. 회의실 3개와 사용자는 시드 데이터로 넣는다.
- 로그인(비밀번호·SSO)은 없다. 화면 상단에서 "나는 누구인지"를 목록에서 고른다. 사내 데모용 간이 식별이며 보안 수단이 아니다. (7장 참조)

## 3. 기능 요구사항

MoSCoW: Must(필수) / Should(권장) / Could(여유 시) / Won't(이번에 안 함).
**Phase 1에는 Must만 넣는다.** Should·Could는 Phase 2 이후에 둔다.

| ID | 기능 | MoSCoW | Phase | 설명 |
|---|---|---|---|---|
| F-01 | 하루 시간표 보기 | Must | 1 | 오늘 날짜, 회의실 3개 × 30분 칸(09:00~18:00)을 표로 보여 준다. 예약된 칸에는 예약자 이름을 표시한다. |
| F-02 | 빈 칸 클릭 예약 | Must | 1 | 빈 칸을 누르면 현재 선택한 사용자 이름으로 그 30분 칸이 예약된다. |
| F-03 | 내 예약 취소 | Must | 1 | 내 예약 칸을 누르면 취소할 수 있다. 다른 사람 예약은 취소할 수 없다. |
| F-04 | 사용자 선택 | Must | 1 | 상단 목록에서 가상 사용자를 고른다. 선택값은 브라우저에 기억한다. "내 예약" 판단의 기준이다. |
| F-05 | 중복 예약 방지 | Must | 1 | 같은 회의실·같은 칸에 동시에 두 건이 생기지 않도록 서버와 DB에서 막는다. |
| F-06 | 가상 시드 데이터 | Must | 1 | 회의실 3개, 사용자 5명, 예시 예약 몇 건을 최초 실행 시 자동으로 넣는다. |
| F-07 | 날짜 이동 | Should | 2 | 이전/다음 날, 날짜 선택으로 다른 날 시간표를 본다. |
| F-08 | 여러 칸 연속 예약 | Should | 2 | 시작 칸에서 끝 칸까지 끌거나 두 번 눌러 한 번에 예약한다. |
| F-09 | 예약 제목 입력 | Should | 2 | 예약 시 회의 제목(선택)을 적고 칸에 표시한다. |
| F-10 | 내 예약 목록 | Could | 3 | 오늘 이후 내 예약을 목록으로 모아 보고 거기서 취소한다. |
| F-11 | 모바일 화면 최적화 | Could | 3 | 좁은 화면에서 가로 스크롤 없이 쓸 수 있게 한다. |

## 4. 화면 구성

화면은 **한 페이지(`index.html`)** 하나다.

### 4.1 레이아웃 (Phase 1)
```
┌──────────────────────────────────────────────┐
│ 회의실 예약        오늘: 2026-10-30   [사용자 ▼] │  ← 헤더
├────────┬───────────┬───────────┬───────────┤
│  시간   │ 회의실 A   │ 회의실 B   │ 회의실 C   │
├────────┼───────────┼───────────┼───────────┤
│ 09:00  │  (빈 칸)   │  김가온    │  (빈 칸)   │
│ 09:30  │  (빈 칸)   │  김가온    │  (빈 칸)   │
│  ...   │           │           │           │
│ 17:30  │  (빈 칸)   │  (빈 칸)   │  이나래    │
└────────┴───────────┴───────────┴───────────┘
 범례: [빈 칸] [내 예약] [다른 사람 예약] [지난 시간]
```

### 4.2 칸 상태와 동작
| 상태 | 표시 | 클릭 시 |
|---|---|---|
| 빈 칸 | 흰 바탕 | 예약 생성 (F-02) |
| 내 예약 | 강조색 + 내 이름 | 취소 확인 후 취소 (F-03) |
| 다른 사람 예약 | 회색 + 예약자 이름 | 아무 일도 없음 |
| 지난 시간 | 흐린 회색 | 아무 일도 없음 |

- 예약·취소 후 시간표를 서버에서 다시 받아 화면을 갱신한다.
- 오류(이미 예약됨 등)는 화면 상단에 한 줄 메시지로 보여 준다.
- 취소는 실수 방지를 위해 확인창(`confirm`)을 한 번 거친다. 예약은 확인 없이 바로 된다.

### 4.3 서버 API (요약)
| 메서드 | 경로 | 용도 |
|---|---|---|
| GET | `/api/rooms` | 회의실 목록 |
| GET | `/api/users` | 사용자 목록 |
| GET | `/api/schedule?date=YYYY-MM-DD` | 해당 날짜 시간표 (Phase 1은 오늘만 허용) |
| POST | `/api/bookings` | 예약 생성 (`room_id`, `slot_start`, `user_id`) |
| DELETE | `/api/bookings/{id}` | 예약 취소 (요청 사용자가 예약자일 때만) |

## 5. 데이터 구조

표 이름 접두어는 **`mr_`** (meeting room). SQLite 단일 파일.

### 5.1 mr_rooms
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | INTEGER PK | 회의실 번호 |
| name | TEXT NOT NULL UNIQUE | 예: 회의실 A |
| capacity | INTEGER | 수용 인원 (가상 값, 표시용) |

### 5.2 mr_users
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | INTEGER PK | 사용자 번호 |
| name | TEXT NOT NULL | 가상 이름 (예: 김가온) |

### 5.3 mr_bookings
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | INTEGER PK | 예약 번호 |
| room_id | INTEGER NOT NULL | → mr_rooms.id |
| user_id | INTEGER NOT NULL | → mr_users.id (예약자) |
| booking_date | TEXT NOT NULL | `YYYY-MM-DD` |
| slot_start | TEXT NOT NULL | 칸 시작 시각 `HH:MM` (09:00 ~ 17:30) |
| status | TEXT NOT NULL | `ACTIVE` 또는 `CANCELLED` |
| title | TEXT NULL | 회의 제목 (Phase 2의 F-09 전까지 비워 둠) |
| created_at | TEXT NOT NULL | 생성 시각 |
| cancelled_at | TEXT NULL | 취소 시각 |

- 유일성: `(room_id, booking_date, slot_start)` 조합은 `status='ACTIVE'`인 행에서 하나만 존재한다 (부분 유니크 인덱스). 취소 후 같은 칸을 다시 예약할 수 있게 하기 위함이다.
- 취소는 행 삭제가 아니라 `status`를 `CANCELLED`로 바꾸는 방식이다. (이력 보존)

### 5.4 시드 데이터 (모두 가상)
- 회의실: 회의실 A(4명), 회의실 B(8명), 회의실 C(12명)
- 사용자: 김가온, 이나래, 박도윤, 최서연, 정하람
- 예시 예약: 오늘 날짜에 2~3건 (화면 확인용)

## 6. 업무 규칙

| ID | 규칙 |
|---|---|
| R-01 | 예약 단위는 30분 한 칸이다. 칸은 09:00부터 17:30까지 18개이며, 마지막 칸은 18:00에 끝난다. |
| R-02 | 같은 회의실의 같은 날짜·같은 칸에는 유효한(ACTIVE) 예약이 하나만 있을 수 있다. 이미 예약된 칸을 예약하려 하면 거절하고 "이미 예약된 시간입니다"를 보여 준다. |
| R-03 | 예약자 본인만 자기 예약을 취소할 수 있다. 다른 사람 예약을 취소하려는 요청은 서버가 거절한다. |
| R-04 | 이미 시작된 칸(현재 시각 이전에 시작한 칸)은 예약할 수 없다. |
| R-05 | 이미 시작된 칸의 예약은 취소할 수 없다. (지난 기록 보존) |
| R-06 | 이미 취소된 예약은 다시 취소할 수 없다. 같은 칸은 다시 예약할 수 있다. |
| R-07 | Phase 1에서는 오늘 날짜만 예약·조회할 수 있다. 다른 날짜 요청은 거절한다. |
| R-08 | 한 번의 클릭은 정확히 한 칸을 예약한다. (여러 칸은 F-08에서 다룸) |
| R-09 | 1인당 예약 개수 제한은 두지 않는다. |
| R-10 | 모든 시각은 한국 표준시(KST) 기준이다. |
| R-11 | 시간표에 보이는 모든 이름과 데이터는 가상 데이터다. |

## 7. 제약 조건

- 기술: Python FastAPI, 순수 HTML/JS(프레임워크·번들러·npm 없음), SQLite만 사용한다. 외부 서비스·외부 DB는 쓰지 않는다.
- 데이터: 가상 데이터만 사용한다. 실제 직원 이름·메일·회의 내용을 넣지 않는다.
- 인증: 사용자 선택은 신뢰 기반의 간이 식별이다. 누군가 다른 사람인 척 선택할 수 있으며, 이번 범위에서는 허용한다. 실제 사내 배포 전에는 인증이 필요하다.
- 동시성: 두 사람이 같은 칸을 동시에 누르면 한 명만 성공해야 한다. 앱 코드의 사전 확인과 DB의 유니크 인덱스를 함께 쓴다.
- 배포: 개발용 단일 서버(`uvicorn`)에서 로컬 실행을 기준으로 한다. 사용자 수십 명 이하를 가정한다.
- 브라우저: 최신 Chrome/Edge 기준.

## 8. 범위 밖

이번 버전에서 하지 않는 것 (Won't):
- 로그인·비밀번호·SSO·권한 관리
- 관리자 화면 (회의실 추가·삭제·수정, 사용자 관리)
- 반복 예약(매주 등), 예약 변경(이동·시간 수정)
- 알림(메일·메신저), 캘린더 연동(Outlook·Google)
- 예약 승인 절차, 참석자 초대
- 장비·시설 예약, 회의실 사진·위치 안내
- 통계·리포트, 다국어
- 실제 직원·회의실 데이터 연동

(날짜 이동·연속 예약·제목·내 예약 목록·모바일 최적화는 범위 밖이 아니라 3장에 적은 대로 Phase 2~3으로 미룬 항목이다.)

## 9. 개발 단계

| Phase | 목표 | 포함 기능 | 비고 |
|---|---|---|---|
| 1 | 오늘 시간표를 보고, 예약하고, 내 예약을 취소한다 | F-01 ~ F-06 (Must만) | 이 단계가 끝나면 데모 가능 |
| 2 | 쓰기 편하게 다듬는다 | F-07, F-08, F-09 (Should) | Phase 1 완료 후 착수 |
| 3 | 편의 기능 | F-10, F-11 (Could) | 여유 있을 때 |

### Phase 1 작업 순서
1. DB 초기화: `mr_rooms`, `mr_users`, `mr_bookings` 생성과 시드 데이터 (F-06)
2. 시간표 조회 API와 화면 표 그리기 (F-01)
3. 사용자 선택 (F-04)
4. 예약 생성 API와 클릭 연결, 중복 방지 (F-02, F-05)
5. 예약 취소 API와 클릭 연결 (F-03)
6. 10장 체크리스트로 전체 확인

## 10. 완료 기준

Phase 1은 아래 항목이 모두 체크되면 끝난다. (괄호는 관련 기능·규칙)

### 시간표
- [ ] T-01 앱을 처음 실행하면 DB가 만들어지고 회의실 3개·사용자 5명·예시 예약이 들어 있다. (F-06, R-11)
- [ ] T-02 화면에 회의실 3열 × 18행(09:00~17:30) 표가 보이고, 마지막 행이 17:30이다. (F-01, R-01)
- [ ] T-03 예약된 칸에 예약자 이름이 보이고, 내 예약·다른 사람 예약·지난 시간·빈 칸이 시각적으로 구분된다. (F-01)

### 예약
- [ ] T-04 사용자를 선택하고 빈 칸을 누르면 그 칸이 내 이름으로 예약되고 화면에 바로 반영된다. (F-02, F-04)
- [ ] T-05 새로고침해도 방금 예약이 유지되고, 선택한 사용자도 유지된다. (F-04, F-06)
- [ ] T-06 이미 예약된 칸에 예약을 보내면(두 브라우저에서 같은 칸 동시 시도 포함) 한 건만 성공하고 나머지는 "이미 예약된 시간입니다"가 나온다. (F-05, R-02)
- [ ] T-07 이미 시작된 칸은 눌러도 예약되지 않고, API로 직접 보내도 서버가 거절한다. (R-04)
- [ ] T-08 오늘이 아닌 날짜로 조회·예약 요청을 보내면 서버가 거절한다. (R-07)

### 취소
- [ ] T-09 내 예약 칸을 누르고 확인창에서 승인하면 예약이 취소되어 빈 칸으로 돌아온다. (F-03)
- [ ] T-10 확인창에서 취소(거절)하면 예약이 그대로 남는다. (F-03)
- [ ] T-11 다른 사람 예약은 화면에서 눌러도 반응이 없고, API로 직접 취소를 보내도 서버가 거절한다. (R-03)
- [ ] T-12 이미 시작된 칸의 예약은 취소할 수 없다. (R-05)
- [ ] T-13 취소한 칸을 다시 예약할 수 있고, 이미 취소된 예약을 다시 취소하면 거절된다. (R-06)

### 마무리
- [ ] T-14 `mr_bookings`에서 취소한 예약이 삭제되지 않고 `status='CANCELLED'`와 `cancelled_at`으로 남아 있다. (5.3)
- [ ] T-15 프레임워크·번들러 없이 FastAPI + 순수 HTML/JS + SQLite만으로 실행되고, 데이터에 실제 개인정보가 없다. (7장)
- [ ] T-16 3장의 Should·Could 기능(F-07~F-11)이 Phase 1 결과물에 포함되어 있지 않다. (3장, 9장)
