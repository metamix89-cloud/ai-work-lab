# 회의실 예약 웹앱 PRD

- 조직: 다온소프트 (사내용)
- 문서 상태: 초안 v0.2 (점검표 5문항 반영)
- 기술: Python FastAPI + 순수 HTML/JS + SQLite
- 데이터: 가상 데이터만 사용 (실제 직원·개인정보 없음)

---

## 1. 개요

### 1.1 배경
회의실 예약을 메신저·구두로 하다 보니 같은 시간에 겹치거나, 누가 쓰는지 알기 어렵다. 한 화면에서 회의실 상태를 보고 바로 예약·취소할 수 있는 간단한 사내 웹앱을 만든다.

### 1.2 목표
- 회의실 3개의 하루 시간표(09:00~18:00, 30분 단위 18칸)를 한 화면에서 본다.
- 시간표의 빈 칸을 눌러 예약한다.
- 내가 한 예약은 내가 취소할 수 있다.

### 1.3 성공 기준 (요약)
- 같은 회의실·같은 시간에 중복 예약이 생기지 않는다.
- 조회 → 예약 → 취소까지 화면 이동 없이 한 화면에서 끝난다.
- 상세 기준은 10장 참고.

### 1.4 범위 원칙
- **Phase 1에는 Must 기능만 넣는다.** Should/Could는 이후 Phase로 미룬다.
- 가장 작은 형태로 먼저 만든다. 인증, 알림, 관리자 기능은 만들지 않는다.

## 2. 사용자

| 구분 | 설명 | 주요 행동 |
|---|---|---|
| 직원 (일반 사용자) | 다온소프트 사내 직원. 유일한 사용자 유형 | 시간표 조회, 예약, 본인 예약 취소 |

- 로그인은 없다. 화면에서 가상 직원 목록 중 "나"를 선택해 본인을 구분한다. (보안 인증이 아니라 단순 구분이며, 사내 소규모 사용 전제)
- 관리자 역할은 두지 않는다.

### 2.1 권한 표

| 행위 | 누가 | 대상 | 허용 여부 | 서버 검사 |
|---|---|---|---|---|
| 시간표 조회 | 직원 누구나 | 모든 예약 | 허용 (이름 포함 공개) | 없음 |
| 예약 생성 | 선택된 "나" | **본인 명의**로만 | 허용 | 요청의 `user_id` 가 `mr_users` 에 존재해야 함. 없으면 404 |
| 예약 취소 | 선택된 "나" | **본인이 만든 예약**만 | 허용 | 예약의 `user_id` ≠ 요청의 `user_id` 이면 403 |
| 타인 예약 취소 | 누구도 | 남의 예약 | **금지** (관리자도 없음) | 403 |
| 예약 완전 삭제 | 누구도 | 모든 예약 | **금지** (취소는 `status` 변경만, R-07) | 삭제 API 자체가 없음 |
| 회의실·직원 추가/수정/삭제 | 누구도 | `mr_rooms`, `mr_users` | **금지** (시드로만 생성) | 쓰기 API 자체가 없음 |

- **서버도 막는다.** 화면에서 버튼을 숨기는 것에 의존하지 않고, 서버가 모든 쓰기 요청에서 위 검사를 한다.
- 한계(의도된 단순화): 로그인이 없으므로 서버는 `user_id` 가 진짜 본인인지 확인할 수 없다. 서버가 막는 것은 "요청에 실린 `user_id` 와 예약자가 다른 경우"까지다. 따라서 외부 공개 환경에서는 쓰지 않는다. (7장)

## 3. 기능 요구사항

MoSCoW: M = Must, S = Should, C = Could

| F-번호 | 기능 | 설명 | MoSCoW | Phase |
|---|---|---|---|---|
| F-01 | 하루 시간표 보기 | 회의실 3개 × 09:00~18:00 30분 칸(18칸)을 표로 표시. 예약된 칸에는 예약자 이름 표시 | M | 1 |
| F-02 | 사용자 선택 | 가상 직원 목록에서 "나"를 선택. 선택값은 브라우저에 기억 | M | 1 |
| F-03 | 빈 칸 클릭 예약 | 빈 칸 클릭 → 확인 창 → 확인 시 해당 30분 예약 | M | 1 |
| F-04 | 내 예약 취소 | 내 예약 칸 클릭 → 확인 창 → 확인 시 취소 | M | 1 |
| F-05 | 중복 예약 방지 | 서버에서 같은 방·같은 시간 중복을 거부하고 사용자에게 메시지 표시 | M | 1 |
| F-06 | 가상 시드 데이터 | 회의실 3개와 가상 직원 8명을 최초 실행 시 자동 생성 | M | 1 |
| F-07 | 날짜 이동 | 이전/다음 날, 오늘 버튼으로 다른 날짜 시간표 조회·예약 (이동 범위: 오늘 ~ 오늘+30일, 과거 날짜는 조회 불가) | S | 2 |
| F-08 | 연속 시간 예약 | 시작 칸 클릭 후 종료 시간을 골라 30분 초과 예약을 한 번에 생성 (최대 4시간 = 8칸) | S | 2 |
| F-09 | 회의 제목 입력 | 예약 시 제목(선택, 최대 30자)을 입력하고 칸에 표시 | S | 2 |
| F-10 | 내 예약 목록 | 오늘 이후 내 예약을 목록으로 모아 보기 | C | 3 |
| F-11 | 자동 새로고침 | 30초 간격으로 시간표를 갱신해 다른 사람 예약을 반영 | C | 3 |

> Phase 1은 F-01 ~ F-06 (모두 Must)만 포함한다. Phase 1의 시간표는 **오늘 하루**만 다룬다.

## 4. 화면 구성

화면은 단일 페이지 1개다.

### 4.1 레이아웃
```
┌─────────────────────────────────────────────┐
│ 회의실 예약          오늘: 2026-10-30   [나: ▼ 김가온 ] │  ← 상단 바 (F-02)
├──────┬────────────┬────────────┬────────────┤
│ 시간 │ 회의실 A   │ 회의실 B   │ 회의실 C   │
├──────┼────────────┼────────────┼────────────┤
│ 09:00│ (빈 칸)    │ 이서연     │ (빈 칸)    │
│ 09:30│ (빈 칸)    │ 이서연     │ (빈 칸)    │
│  ... │            │            │            │
│ 17:30│ (빈 칸)    │ (빈 칸)    │ 박도윤     │
└──────┴────────────┴────────────┴────────────┘
```
- 행: 09:00 ~ 17:30 시작 칸 18개 (마지막 칸은 17:30~18:00)
- 열: 회의실 3개
- 시각 표기는 24시간제 `HH:MM`, 날짜 표기는 `YYYY-MM-DD`.

### 4.2 칸 상태

| 상태 | 표시 | 클릭 동작 |
|---|---|---|
| 빈 칸 | 흰색 | 예약 확인 창 열기 |
| 내 예약 | 강조색 + 내 이름 | 취소 확인 창 열기 |
| 남의 예약 | 회색 + 예약자 이름 | 동작 없음 |
| 지난 시간 | 흐리게 (빈 칸이든 예약이든 시작 시각이 현재 이하인 칸) | 동작 없음 |

- 지난 시간 칸에 예약이 있으면 예약자 이름은 계속 표시한다. 내 예약이어도 취소 창은 열리지 않는다. (R-06)

### 4.3 확인 창
- 예약: "회의실 A, 10:00~10:30 예약할까요?" [예약] [닫기]
- 취소: "회의실 A, 10:00~10:30 예약을 취소할까요?" [예약 취소] [닫기]
- 확인 버튼을 누른 뒤 응답이 올 때까지 버튼을 비활성화한다. (중복 클릭 방지)
- 실패 시 확인 창을 닫고, 상단 오류 줄에 4.4의 문구를 보여준 뒤 시간표를 다시 불러온다.

### 4.4 빈 상태 · 오류 상태

| 상황 | 서버 응답 | 화면 |
|---|---|---|
| 오늘 예약이 0건 | 200, 빈 목록 `[]` | 시간표는 전부 빈 칸으로 정상 표시. 표 위에 안내 문구 "오늘 예약이 없습니다. 빈 칸을 눌러 예약하세요." |
| "나"를 아직 선택하지 않음 | (요청 보내지 않음) | 시간표 조회는 가능. 칸을 누르면 요청 없이 오류 줄에 "먼저 상단에서 '나'를 선택하세요." |
| 저장된 "나"가 목록에 더는 없음 | — | 선택을 초기화하고 "나" 미선택 상태로 돌린다. |
| 직원 목록이 비어 있음 (시드 실패) | 200, `[]` | 선택 목록 자리에 "직원 정보가 없습니다. 서버를 다시 시작하세요." 표시, 예약·취소 불가 |
| 현재 시각이 18:00 이후 (모든 칸이 지난 칸) | 200 | 시간표 전체가 흐리게 표시되고 안내 문구 "오늘 예약 가능한 시간이 끝났습니다." |
| 서버에 연결할 수 없음 / 5xx | 연결 실패 또는 500 | 시간표 영역에 "서버에 연결할 수 없습니다. 잠시 후 다시 시도하세요." + [다시 불러오기] 버튼. 칸은 클릭 불가 |
| 중복 예약 거부 | 409 | "이미 다른 사람이 예약한 시간입니다." + 시간표 다시 불러오기 |
| 지난 시간 예약 거부 | 422 | "이미 지난 시간은 예약할 수 없습니다." |
| 남의 예약 취소 거부 | 403 | "본인이 만든 예약만 취소할 수 있습니다." |
| 시작했거나 지난 예약 취소 거부 | 422 | "이미 시작했거나 지난 예약은 취소할 수 없습니다." |
| 이미 취소된 예약을 다시 취소 | 409 | "이미 취소된 예약입니다." + 시간표 다시 불러오기 |
| 존재하지 않는 회의실·직원·예약 | 404 | "요청한 정보를 찾을 수 없습니다." + 시간표 다시 불러오기 |
| 형식·범위 오류 (30분 단위가 아님, 09:00~17:30 밖, 오늘이 아닌 날짜 등) | 400 | "잘못된 요청입니다." (정상 화면에서는 발생하지 않음) |

- 오류 줄의 문구는 5초 후 사라지거나 다음 동작 시 사라진다.
- 서버 오류 본문은 JSON `{"detail": "<위 표의 문구>"}` 로 통일하고, 화면은 이 `detail` 을 그대로 보여준다.

## 5. 데이터 구조

SQLite 사용. 모든 표 이름은 `mr_` 로 시작한다. (mr = meeting room)

### 5.1 mr_rooms — 회의실

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | INTEGER PK | 회의실 번호 |
| name | TEXT NOT NULL UNIQUE | 회의실 이름 (A / B / C) |

### 5.2 mr_users — 가상 직원

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | INTEGER PK | 직원 번호 |
| name | TEXT NOT NULL UNIQUE | 가상 이름 |

### 5.3 mr_reservations — 예약

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | INTEGER PK | 예약 번호 |
| room_id | INTEGER NOT NULL | → mr_rooms.id |
| user_id | INTEGER NOT NULL | → mr_users.id (예약자) |
| rsv_date | TEXT NOT NULL | 예약 날짜 `YYYY-MM-DD` |
| slot_start | TEXT NOT NULL | 시작 시각 `HH:MM` (09:00 ~ 17:30, 30분 단위) |
| status | TEXT NOT NULL | `active` / `cancelled` |
| created_at | TEXT NOT NULL | 생성 일시 (KST, `YYYY-MM-DD HH:MM:SS`) |
| cancelled_at | TEXT | 취소 일시 (취소 시에만, 같은 형식) |

- 제약: `(room_id, rsv_date, slot_start)` 조합은 `status = 'active'` 인 행에서 유일해야 한다. (부분 유니크 인덱스) — 중복 방지의 최종 방어선.
- 한 행 = 30분 한 칸. 종료 시각은 저장하지 않고 `slot_start + 30분` 으로 계산한다. Phase 2의 연속 예약(F-08)은 여러 행을 만들어 처리하므로 구조 변경이 필요 없다.
- `rsv_date` 는 Phase 1에서 항상 오늘이지만, Phase 2 날짜 이동을 위해 미리 둔다.

### 5.4 가상 시드 데이터
- 회의실: A, B, C (3개 고정)
- 직원: 가상 이름 **8명** (예: 김가온, 이서연, 박도윤 … 실존 인물과 무관)
- 시드는 표가 비어 있을 때만 1회 실행한다. 재시작해도 중복 생성하지 않는다.
- 예약: 시드는 직원·회의실만 생성. 예약은 사용자가 만든다. (보여주기용 예약이 필요하면 가상 예약 몇 건을 선택적으로 추가)

## 6. 업무 규칙

### 6.1 규칙 표

| R-번호 | 규칙 |
|---|---|
| R-01 | 예약 가능 시간은 09:00~18:00. 30분 단위 칸만 예약할 수 있다. (시작 시각 09:00 ~ 17:30, `:00` 또는 `:30` 만 허용) |
| R-02 | 한 예약은 한 회의실의 한 칸(30분)이다. (Phase 1) |
| R-03 | 같은 회의실·같은 날짜·같은 시간에 활성 예약은 1건만 가능하다. 충돌 판정은 6.2를 따른다. |
| R-04 | 칸의 시작 시각이 **현재 시각 이하**이면 지난 칸이다. 지난 칸은 예약할 수 없다. |
| R-05 | 예약은 예약한 본인만 취소할 수 있다. 서버에서도 예약자와 요청자를 대조한다. (2.1) |
| R-06 | 칸의 시작 시각이 **현재 시각 이하**인 예약은 취소할 수 없다. (이용 기록 보존) R-04와 같은 기준이다. |
| R-07 | 취소는 행을 지우지 않고 `status = 'cancelled'` 로 바꾼다. 취소된 칸은 다시 예약 가능하다. |
| R-08 | 한 사람이 여러 회의실의 같은 시간을 동시에 예약하는 것도 막지 않는다. (Phase 1 단순화) |
| R-09 | 한 사람의 예약 개수 제한은 두지 않는다. (이론상 최대: 하루 3실 × 18칸 = 54건) |
| R-10 | 시간 기준은 서버 시각(한국 표준시, KST)이다. 브라우저 시계는 쓰지 않는다. |

### 6.2 충돌 규칙과 경계

무엇과 무엇이 부딪치면 거부하는가:

| 부딪치는 것 | 판정 | 결과 |
|---|---|---|
| 새 예약 vs 같은 방·같은 날짜·같은 `slot_start` 의 **active** 예약 | 충돌 | 409 "이미 다른 사람이 예약한 시간입니다." (본인 예약이어도 동일) |
| 새 예약 vs 같은 칸의 **cancelled** 행 | 충돌 아님 | 예약 성공 (새 행 생성) |
| 새 예약 vs 다른 방의 같은 시간 | 충돌 아님 | 성공 (R-08, 같은 사람이어도) |
| 새 예약 vs 같은 방의 인접 칸 (예: 10:00~10:30 과 10:30~11:00) | 충돌 아님 | 성공 |
| 새 예약 vs 현재 시각 이하에 시작한 칸 | 거부 | 422 "이미 지난 시간은 예약할 수 없습니다." |
| 새 예약 vs 영업 시간 밖 (08:30, 18:00 등) · 30분 단위 아님 (10:15) | 거부 | 400 |

딱 붙는 경계는 이렇게 처리한다:
- **시간 구간은 `[시작, 종료)` (시작 포함, 종료 미포함)로 본다.** 10:00~10:30 예약의 종료 10:30은 다음 칸 10:30~11:00의 시작과 겹치지 않는다. 따라서 끝과 시작이 딱 붙는 예약은 허용한다.
- **현재 시각과 칸 시작이 정확히 같으면 지난 칸이다.** 예: 지금이 10:00:00이면 10:00 칸은 예약도 취소도 불가, 10:30 칸부터 가능. (R-04, R-06을 같은 기준으로 통일)
- 마지막 칸 17:30~18:00은 예약 가능하다. 시작 시각 18:00 칸은 존재하지 않는다.
- 판정은 요청이 서버에 도착한 시각 기준이다. 화면에서는 가능했더라도 서버 시각에 따라 거부될 수 있다.
- 동시에 같은 칸을 누르면 DB 부분 유니크 인덱스에서 한 건만 성공하고, 나머지는 409로 처리한다. (애플리케이션에서 먼저 조회해 확인하더라도 최종 판정은 DB가 한다.)
- (Phase 2) 연속 예약은 구간 안의 칸 중 **하나라도** 충돌·지난 칸이면 **전부 거부**하고 하나도 만들지 않는다. 한 번에 최대 8칸(4시간), 하루를 넘기거나 18:00을 넘는 구간은 400.

### 6.3 API 요약 (Phase 1)

| 메서드·경로 | 용도 | 성공 | 실패 |
|---|---|---|---|
| `GET /api/rooms` | 회의실 목록 | 200 | 5xx |
| `GET /api/users` | 가상 직원 목록 | 200 | 5xx |
| `GET /api/reservations?date=YYYY-MM-DD` | 해당 날짜의 active 예약 목록 (예약자 이름 포함). Phase 1은 `date` 생략 시 오늘. 오늘이 아닌 날짜는 400 | 200 (없으면 `[]`) | 400 |
| `POST /api/reservations` | 예약 생성. 본문: `room_id`, `user_id`, `slot_start` (날짜는 서버가 오늘로 정함) | 201 | 400 / 404 / 409 / 422 |
| `DELETE /api/reservations/{id}?user_id=N` | 예약 취소 (`status` 변경) | 200 | 403 / 404 / 409 / 422 |

- 오류 상태 코드와 문구는 4.4와 같다.
- 예약·취소는 서버 시각 기준으로 6.2의 검사를 모두 통과해야 한다.

## 7. 제약 조건

- **기술 스택**: 백엔드 Python FastAPI, 프런트 순수 HTML + JavaScript(프레임워크·빌드 도구 없음), DB는 SQLite 파일 1개.
- **구성**: FastAPI가 정적 HTML/JS와 JSON API를 함께 제공하는 단일 서버. 로컬(사내 PC) 실행 기준.
- **데이터**: 가상 데이터만 사용한다. 실제 직원 이름·계정·연락처를 넣지 않는다.
- **인증**: 없음. 사용자 선택 방식은 본인 확인이 아니므로 외부 공개 환경에서 쓰지 않는다.
- **동시성**: 두 사람이 같은 칸을 동시에 누르면 DB 유니크 제약으로 한 명만 성공하고, 다른 한 명은 409 오류 메시지를 받는다.
- **브라우저**: 최신 Chrome/Edge 데스크톱 기준. 모바일 최적화는 하지 않는다.
- **규모**: 회의실 3개, 직원 8명(시드) ~ 최대 50명, 동시 접속 10명 이하의 소규모 사용을 가정한다.
- **성능 목표**: 시간표 조회 응답 1초 이내, 예약·취소 응답 1초 이내 (위 규모 기준).

## 8. 범위 밖

Phase 1뿐 아니라 이 PRD 전체에서 다루지 않는 것:

- 로그인, 비밀번호, SSO 등 실제 인증·권한 관리
- 관리자 화면 (회의실 추가·삭제, 타인 예약 강제 취소)
- 반복 예약, 예약 수정(시간 변경)
- 예약 완전 삭제(행 삭제), 취소 이력 조회 화면
- 이메일·메신저 알림, 캘린더(Outlook/Google) 연동
- 회의실 정원·장비 정보, 승인 절차, 사용 통계
- 모바일 앱 및 모바일 전용 화면
- 실제 직원 데이터 연동
- 한 사람의 동시 예약 제한·예약 개수 제한 (R-08, R-09로 일부러 막지 않음)

이번(Phase 1)에 만들지 않는 것 — 범위 밖이 아니라 **뒤 Phase로 미룬 것**:

- Phase 2: 날짜 이동(F-07), 연속 시간 예약(F-08), 회의 제목(F-09)
- Phase 3: 내 예약 목록(F-10), 자동 새로고침(F-11)
- Phase 1에서는 다른 사람이 만든 예약이 화면에 보이려면 사용자가 직접 새로고침해야 한다.
