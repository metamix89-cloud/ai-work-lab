# PRD — 푸른구청 「민원 접수 · 처리 현황판」

> 「이 화면, PRD 로는 이렇게」 7편. 구청 · 직원 · 민원은 모두 교육용 가상 데이터.
> 형식은 10칸(개요 · 사용자 · 기능 · 화면 · 데이터 · 업무 규칙 · 제약 · 범위 밖 · 개발 단계 · 완료 기준).

## 1. 개요

- **배경:** 푸른구청 민원팀은 민원을 엑셀로 관리한다. 누가 맡았는지, 어디까지 처리됐는지, 기한이 지났는지를 매일 아침 팀장이 행을 훑어 찾는다. '종결' 로 바꿨다가 다시 '처리중' 으로 돌리는 일도 있어 처리 이력이 믿기 어렵다.
- **목적:** 민원이 **접수 → 배정 → 처리중 → 종결** 한 방향으로만 흐르고, 단계마다 필요한 것(담당자 · 답변)이 없으면 넘어가지 못하며, **기한(접수일 + 7일)을 넘긴 건**이 숫자와 표시로 바로 보인다. 모든 단계 이동은 이력으로 남는다.
- **성공 기준:** 기한 넘긴 민원을 찾는 데 걸리는 시간 0. 종결 뒤 되돌린 민원 0건.

## 2. 사용자

- **민원팀 직원 1유형.** 로그인 없이 사내망에서 연다. 화면 위 **처리자 선택 상자**에서 자기 이름을 고르면 이력의 `by` 가 된다(권한 구분은 이 편 범위 밖).

## 3. 기능 요구사항

| 번호 | 기능 | MoSCoW | Phase |
|---|---|---|---|
| F1 | 현황 숫자: 단계별 건수 4개 + 기한 넘김 건수 | Must | 1 |
| F2 | 칸반: 단계별 열 4개, 카드에 제목 · 분야 · 접수일 · 기한(D-n 또는 n일 지남) · 담당자 | Must | 1 |
| F3 | 다음 단계로: 카드 상세에서 '다음 단계' — 배정은 담당자, 종결은 답변이 있어야 | Must | 1 |
| F4 | 이력: 상세에 단계 이동 기록(언제 · 무엇에서 무엇으로 · 누가) | Must | 1 |
| F5 | 기한 넘김 강조: 종결되지 않았고 기한이 지난 카드는 빨간 테두리 | Must | 1 |
| F6 | API: `GET /api/staff` · `GET /api/summary` · `GET /api/complaints` · `GET /api/complaints/{id}` · `POST /api/complaints/{id}/transition` · `GET /api/complaints/{id}/history` | Must | 1 |

## 4. 화면

한 페이지(`/`). 위에서 아래로:

- **위:** 제목 `푸른구청 민원 현황판`, 처리자 선택(`data-testid="actor"`, `/api/staff` 이름), 기준일(`data-testid="as-of"`, `/api/summary` 의 `as_of`).
- **현황 숫자:** 단계마다 `data-testid="count"` + `data-status="접수|배정|처리중|종결"`, 그리고 기한 넘김 `data-testid="overdue-count"`.
- **칸반:** 열 4개 `data-testid="column"` + `data-status`. 카드 `data-testid="complaint"`, 속성 `data-id` · `data-overdue="1|0"`. 카드는 자기 상태의 열 안에 있다. 기한 넘김 카드는 빨간 테두리와 `n일 지남`.
- **상세(카드를 누르면):** 제목 · 내용 · 담당자 · 답변, 다음 단계 버튼(`data-testid="next-btn"`, 종결이면 없음). 배정으로 갈 때 담당자 선택(`data-testid="assignee"`), 종결로 갈 때 답변 입력(`data-testid="answer"`). 이력 목록(`data-testid="history-item"`).
- **메시지 줄:** `data-testid="message"` — 서버가 거부하면 `detail` 그대로.
- **오류 상태:** API 가 실패하면 `불러오지 못했습니다` 와 다시 시도 버튼.
- 시각 요소 이름은 완료 기준 테스트가 집는 손잡이다. 문구를 테스트하는 요소는 그 문구가 **손잡이 요소 안에** 있어야 한다.

## 5. 데이터

- **원본:** 프로젝트 루트 `seed/` CSV 2개. 서버는 **시작할 때마다** CSV 를 읽어 SQLite(`civil.db`)를 **새로** 만든다. 단계 이동과 이력은 DB 에 쓴다.
  - `seed/staff.csv` — `name, team`
  - `seed/complaints.csv` — `complaint_id, title, category, received(YYYY-MM-DD), status(접수|배정|처리중|종결), assignee(빈칸 가능), answer(빈칸 가능)`
- (실측 뒤 메모: 칸 이름만 적고 **형식**을 적지 않았다 — `complaint_id` 가 문자열(예 `C-01`)인지 숫자인지. B3 은 정수로 읽어 테스트 데이터에서 서버가 죽었다(0/9). 공개본에는 빈틈을 그대로 둔다 — 7편 영상의 재료. 데이터 계약은 칸 이름 + 형식 + 예시 한 줄.)
- **테이블:** 접두어 `cv_` — `cv_staff` · `cv_complaints` · `cv_history(complaint_id, from_status, to_status, at, by)`. seed 의 민원은 이력이 없이 시작한다.
- **기준일:** 서버의 오늘 날짜 하나. `GET /api/summary` 와 `GET /api/complaints` 가 `as_of` 로 돌려준다. 화면은 따로 계산하지 않는다.
- **가상 데이터:** 직원 4명, 민원 8건(단계마다 1~3건, 기한 넘김 2건, 기한 당일 1건). **같은 CSV 를 다른 내용으로 바꿔 끼울 수 있어야** 한다.
- **API**
  - `GET /api/staff` → `[{"name":"김민수","team":"민원1팀"}, ...]`
  - `GET /api/summary` → `{"as_of":"2026-10-24","counts":{"접수":3,"배정":1,"처리중":2,"종결":2},"overdue":2}`
  - `GET /api/complaints?status=` → `{"as_of","items":[{"complaint_id","title","category","received","status","assignee","due","days_left","overdue"}]}` — `due` = 접수일 + 7일, `days_left` = due − 기준일(음수면 지남), `overdue` 는 R4.
  - `GET /api/complaints/{id}` → 위 칸 + `answer`. 없으면 404.
  - `POST /api/complaints/{id}/transition` 본문 `{"to":"배정","by":"최팀장","assignee":"이서준","answer":""}` → 200 과 갱신된 민원. 거부는 R7 순서.
  - `GET /api/complaints/{id}/history` → `[{"from_status","to_status","at":"YYYY-MM-DD HH:MM","by"}]` 오래된 것 먼저.
  - 거부 응답은 모두 `{"detail": "사유"}`.

## 6. 업무 규칙

| 번호 | 규칙 |
|---|---|
| R1 | **한 방향 한 칸씩.** 접수 → 배정 → 처리중 → 종결. 다음 칸이 아니면 409 — 뒤로 가면 `상태를 되돌릴 수 없습니다`, 건너뛰면 `단계를 건너뛸 수 없습니다`. |
| R2 | **배정에는 담당자.** `to=배정` 이면 `assignee` 가 직원 목록에 있어야 한다. 없거나 모르는 이름이면 400 `담당자를 선택하세요`. |
| R3 | **종결에는 답변.** `to=종결` 이면 `answer` 가 공백 아닌 글이어야 한다. 아니면 400 `답변을 입력하세요`. |
| R4 | **기한 넘김** = 종결이 아니고 기준일 > `due`(접수일 + 7일). **기한 당일은 넘김이 아니다.** 종결된 건은 기한이 지났어도 넘김이 아니다. |
| R5 | **종결은 잠금.** 종결된 민원에 어떤 이동이든 409 `종결된 민원입니다`. |
| R6 | **이동마다 이력 한 줄.** 200 으로 끝난 이동만 기록한다(거부된 시도는 기록하지 않는다). `by` 가 직원 목록에 없으면 400 `처리자를 선택하세요`. |
| R7 | **거부가 둘 이상 해당하면** 400(입력 오류: `to` 가 네 단계가 아님 · by · assignee · answer) → 404(없는 민원) → 409(흐름 위반) 순서로 먼저 걸리는 것 하나만. |

## 7. 제약

- 스택: **Python FastAPI + 순수 HTML/JS(프레임워크 · 빌드 도구 없음) + SQLite.** 드래그 앤 드롭 라이브러리 금지(버튼으로 이동).
- 실행: 프로젝트 루트에서 `python -m uvicorn main:app --port 8000` (`main.py` 에 `app = FastAPI()`). 포트는 환경 변수 `PORT` 가 있으면 그것.
- 외부 네트워크 · CDN 없음. 외부 패키지는 `fastapi` · `uvicorn` 만. 한글 UI.

## 8. 범위 밖 (Won't)

- 로그인 · 권한(팀장만 배정 등), 민원 등록 · 수정 · 삭제 화면(민원 접수는 다른 시스템), 주민 알림(문자 · 메일), 드래그 앤 드롭, 공휴일을 뺀 기한 계산, 재접수 · 이관, 첨부 파일, 통계 차트, 엑셀, 다크 모드.

## 9. 개발 단계

1. **Phase 1:** `seed/` → SQLite, API 6개와 규칙 R1~R7, `/` 화면(현황 숫자 · 칸반 · 상세 · 다음 단계 · 이력 · 메시지 · 오류).
2. 그 외 없음.

## 10. 완료 기준 (DoD)

`tests/test_dod.py` 가 완료 기준이다. 아래 9개가 모두 통과해야 끝난다.

- [ ] T1 `/` 가 200 으로 열리고 '민원' 이 보인다.
- [ ] T2 `summary` 의 단계별 건수(3 · 1 · 2 · 2)와 기한 넘김 2, `as_of` 가 오늘이다.
- [ ] T3 기한 넘김 판정 — 8일 전 접수 처리중은 넘김, 7일 전 접수(기한 당일)는 아님, 10일 전 접수 종결은 아님. `days_left` 가 맞다 (R4).
- [ ] T4 접수 → 배정(담당자 있음)은 200, 상태가 배정이 된다.
- [ ] T5 건너뛰기(접수 → 처리중) · 되돌리기(처리중 → 배정) · 종결된 건 이동은 모두 409 (R1 · R5).
- [ ] T6 담당자 없는 배정 · 모르는 담당자 · 답변 없는 종결 · 모르는 처리자는 400 (R2 · R3 · R6).
- [ ] T7 없는 민원 + 잘못된 본문은 400, 없는 민원 + 올바른 본문은 404 (R7).
- [ ] T8 이력이 성공한 이동만, 오래된 것 먼저, from · to · by 가 맞게 남는다 (R6).
- [ ] T9 화면: 열 4개, 카드가 자기 상태 열 안에, 기한 넘김 카드 `data-overdue="1"`, `overdue-count` 가 API 값과 같다.
