# 가나다식품 LLM 위키 실험 — 작업 기록

개념 출처: Andrej Karpathy, "LLM Wiki" (GitHub Gist, 2026-04-04, gist.github.com/karpathy/442a6bf555914893e9891c11519de94f). 세 층(raw 원본 · wiki 페이지 · schema) · index.md · log.md · 세 작업(ingest · query · lint).
"intentionally abstract" 한 글이라 폴더 이름은 우리가 정했다. 라이선스 표기는 없음 → "아이디어를 바탕으로 AI워크랩이 업무용으로 재구성" 으로 표기(1편 원작 소개 장면).
Karpathy 의 숫자: 원본 하나가 10~15 페이지를 건드림, index 방식은 ~100 원본 · 수백 페이지까지. 우리 실험은 원본 67개라 그 안.

## 파일
- WORLD.md — 가상 세계의 사실(정답 근거). 숫자는 여기가 기준.
- make_sources.py → raw/ (원본 67개: cs 16 · suppliers 8 · customers 9 · meetings 12 · policies 6 · sales 6 · ops 10) + planted.json (심은 모순 C1~C20 중 19개 · 민감 정보 P1~P10)
  - C2(반품 7일 vs 14일)는 '날짜 조건' 이라 planted 에 따로 넣지 않음 → lint 정답은 "둘 다 맞음, 시행일 조건" 으로 채점.
- schema.md — 위키 규칙(페이지 종류 · 형식 · 쓰면 안 되는 것)
- engine.py — ingest / query / lint + baseline_dump / RAG. 자가 시험 통과(한빛물류 요금표 넣기 → 제주 냉동 5,700원 답, 근거 페이지 표시).
- questions.json — 50문항(Q1~Q5 × 10, fact 30 · evidence 2 · none 5 · date 8 …). grade.py 자가 시험 13건.

## 실험 설계 (편별)
- 1편: 조건 ① 원본 전부 프롬프트 ② RAG(하이브리드 top-8) ③ 빈 위키 → Q1~Q5 50문항 × 3회. 위키는 아직 없으니 ③ 은 "위키에 없음" 만 나와야 함(= 0/5 그룹).
- 2편~: 그룹별 원본을 차례로 ingest 하며 ③ 의 점수가 오르는 것을 보여 준다. 편마다 wiki 스냅샷 저장(wiki_ep0NN/).
- 결과 파일: results/ep0NN_*.json

위키 빌드 비용: 57개 원본, 22분, 262만 토큰(원본당 4.6만), 원본당 평균 3.4페이지 수정(Karpathy 의 10~15 보다 작음 — 원본이 짧아서).

**1편에서 그대로 밝힐 것 — 위키는 '한 번에 다 넣으면' RAG 보다 못했다.**
1. 규정(Q4)은 위키가 30/30 으로 가장 셌다. 개정 이력을 페이지에 모아 두니 '식비 12,000'(7/1 개정)을 RAG(10,000 으로 세 번 틀림) · 원본 통째보다 잘 맞혔다.
2. 결정 · 이유(Q3)는 위키가 15/30 으로 가장 약했다. **약한 원본(영업 메모)이 센 원본(회의록 · 계약서)을 덮어썼다**: 참기름 인상 '10%'(메모, 정답 12%), 바사푸드 납품 '화 · 목'(메모, 계약은 화 · 금 — 심지어 이력에 "화,금 → 화,목" 으로 적음), 김 선물세트 '단종됨'(메모, 결정은 보류), 홍삼 젤리 '약 300박스'(메모, 재고표 500). schema 에 "메모 · 초안은 근거가 약하다, 센 쪽을 현재 값으로" 라고 써 두었는데 **넣는 순서상 메모가 나중에 들어오자 '최신 = 현재 값' 으로 처리**했다. → 2~5편에서 ① 원본에 등급(계약서 > 공문 > 회의록 > 메모)을 파일명 · 머리말로 표시 ② 상충 섹션에 두 값을 남기게 하는 규칙으로 고치고 다시 잰다. 이게 시리즈의 핵심 교훈(원본에 등급이 없으면 위키는 마지막 말을 믿는다).
3. 민감 정보: schema 에 '쓰면 안 되는 것' 이 있었는데도 **초기 비밀번호(P7)가 부서/고객센터 페이지에, 인사위 회부(P9)가 목차에** 옮겨졌다(leak_check.py 2/10). 나머지 8개는 막았다. 11편 재료.
4. 목차에 '## 부서' 절이 두 번 생겼고, FAQ 초안(옛 값)이 '규정/반품-배송-출장-경비' 페이지로 따로 들어갔다(lint 가 잡아야 할 것 — 6편).
5. 회의록의 '논의 · 보고' 절 숫자(변질 반품 비용 2,300만 원)는 결정 페이지에 안 들어갔다 → Q1-06 0/3. 페이지 종류 '지표' 로 보내는 규칙 필요.
6. RAG 가 틀린 곳: 개정 전 값(식비 10,000) 3/3, 두 문서 결합(제주 냉동 4,200+1,500 → 11/15 인상분 4,500 을 섞어 6,000) 3/3, 날짜 조건 판단(법인카드 10/5 — '네 필요했다' 하고 스스로 정정) 3/3.
7. 원본 통째는 '오늘 기준 단가' 에 미래 단가(79,270)를 답함 3/3 — 자료가 많으면 날짜 조건을 놓친다. 그리고 문항당 3.3만 토큰(RAG 의 15배).

채점기 수정 기록(영상에서 밝힘): ① 날짜 표기(2026-11-01 · 11월 1일 → 11/1) 통일 ② 대안 값을 must 로 잘못 적은 4문항(any 로) ③ '승인 가능하여 … 불가' 오답 처리 ④ 근거 설명에 상충 원본을 인용한 것을 오답 처리 → '답:' 부분만 검사 ⑤ "0건" 을 없음으로 인정 ⑥ Q1-04 지역 이름 답 인정. 재채점으로 32건 판정이 바뀜(dump +2, rag +17, full +13).
질문 문구 결함(다음 편에서 고침): Q3-10 '근거' → '이유' (모델이 출처로 읽음), Q5-05 '밀면 안 되는' → '판촉에 넣으면 안 되는' (밀키트로 읽음).

## 3편 실험 (2026-10-23) — 공급사 8 + 매출처 9 파일을 2편 v4 위키 위에

기본(schema_ep2c + tally + auto-index, wiki_ep3): Q2 10문항 × 3 = **위키 27/30, RAG 30/30**. 21페이지 · 고아 0 · 상충 섹션 채운 페이지 7.
- 1편 때 메모가 덮어썼던 값들(참기름 10% · 바사푸드 화목 · 선물세트 단종 · 홍삼 300)이 이번엔 **하나도 안 들어갔다**. 다나유통 2.5% 만 '상충' 에 들어감. '한 번에 새 페이지 3개' 와 집계 규칙이 메모의 영향을 줄인 듯(원인은 단정 못 함 — 1편은 57개를 한 번에, 여기선 17개).
- 가나공급 페이지에 단가 현황 표(적용일 포함) + 이력이 제대로 들어감.
- 틀린 것: Q2-02(11/5 견적 매입 단가 79,270) — '거래처/단가표' 라는 페이지(상품_단가표에서 생김)를 열어 공급가 91,800 을 답함. 질문 문구도 애매해 '가나공급 매입 단가' 로 고침.
- 추가 문항 Q2-11(단가 이력) · Q2-12(담당 변경) · Q2-13(보냉재 현재 값 + 적용일): RAG 9/9, 위키 4/9. Q2-11 은 또 '거래처/단가표' 페이지만 열고 "이력 없음" — 같은 품목의 단가가 두 페이지에 갈라져 묻기가 이력 없는 쪽을 연다. Q2-12 는 채점기 오탐("이전 담당은 이 대리") → not 규칙 고쳐 재채점.
- 3편 규칙(schema_ep3.md): 원본 등급(기록 · 계약 > 공문 > 회의록 > 보고 > 메모, 낮은 등급은 덮어쓰기 금지) · 현재 값과 이력 분리(미래 값은 '예정') · 단가 이력 표 · 누적 표 · **한 품목의 단가는 상품 페이지 한 곳(+거래처 페이지)** → ep3r 실행.

- **규칙 v1(ep3r, 글로 쓴 등급 · 이력 규칙): 28/45 로 하락.** 구매팀 메모(등급 5)가 4번째로 들어와 '상품/떡볶이소스' 페이지를 먼저 만들었고(10% · 47,000), 단가표는 '상품/떡볶이-소스-2kg' 로 따로 → 묻기가 메모 페이지를 엶. '미래 값은 예정' 규칙을 11/5 견적 질문에도 적용(73,400), 제주 요금은 거꾸로 11/15 예정값(6,000). 46페이지 · 상충 31.
